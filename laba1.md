# Анализ предметной области: Информационная система медицинских организаций

## Цель и задачи проекта

### Основная цель  
Разработка информационной системы для автоматизации учета пациентов, медицинского персонала и ресурсов больниц и поликлиник с целью повышения эффективности управления лечебным процессом и формирования оперативной отчетности.

## Основные задачи проекта

Чтобы система получилась рабочей и полезной, нам нужно пройти несколько ключевых этапов:

1.  **Глубокий анализ предметной области**
    *   Разобраться в структуре медицинских учреждений (больницы -> корпуса -> отделения -> палаты).
    *   Изучить специфику работы разных врачей (хирурги, рентгенологи и т.д.) и их уникальные атрибуты (стаж, вредность, звания).
    *   Понять логику движения пациентов: от поликлиники до стационара и операций.

2.  **Проектирование модели данных**
    *   Спроектировать базу данных, которая сможет хранить сложную иерархию зданий и отделений.
    *   Реализовать наследование или гибкую структуру для хранения специфических данных о разных типах врачей (например, количество операций только для хирургов).
    *   Учесть возможность совместительства врачей и консультаций профессоров в нескольких местах.

3.  **Разработка функционала учета и отчетности**
    *   Реализовать ведение электронных карт пациентов (история болезней, назначения, температура).
    *   Настроить систему запросов для получения статистики по кадрам, загруженности коек и выработке врачей/лабораторий.
    *   Обеспечить связь между поликлиниками, больницами и лабораториями через договоры.

4.  **Тестирование сценариев использования**
    *   Проверить корректность распределения пациентов по палатам (учет свободных коек).
    *   Убедиться, что отчеты по операциям и стажу работы формируются верно для разных категорий врачей.

5.  **Подготовка документации**
    *   Описать архитектуру системы и схему базы данных.
    *   Составить руководство пользователя для медперсонала и администраторов.

## Основные требования  

- **Учет структуры учреждений:** Система должна поддерживать иерархию: Город -> Больница/Поликлиника -> Корпус (для больниц) -> Отделение -> Палата/Кабинет.
- **Гибкий учет персонала:** Возможность вести учет врачей разных профилей с уникальными характеристиками (коэф. вредности, кол-во операций, ученые степени) и обслуживающего персонала.
- **Совместительство:** Поддержка работы одного врача в нескольких учреждениях (основное место + совместительство/консультации).
- **Маршрутизация пациентов:** Логика направления пациентов из поликлиники в больницу (как прикрепленную, так и стороннюю при отсутствии специализации).
- **История лечения:** Полное хранение анамнеза, назначений, результатов анализов и операций для каждого пациента.
- **Лаборатории:** Учет договоров с лабораториями и результатов анализов различных профилей (биохимия, физиология и др.).

## Основная функциональность проекта  

- **Реестр учреждений:** Ведение справочника больниц, поликлиник, их корпусов и отделений с указанием количества коек и кабинетов.
- **Кадровый учет:** Регистрация врачей и медперсонала, присвоение категорий, званий (доцент, профессор) и фиксация мест работы.
- **Управление пациентами:** 
  - Амбулаторный прием в поликлиниках (запись к нескольким врачам).
  - Стационарное лечение в больницах (закрепление за одним лечащим врачом, размещение в палате).
  - Ведение истории болезни и температурного листа.
- **Учет медицинской деятельности:** 
  - Фиксация проведенных операций (с исходами) для хирургов.
  - Запись результатов лабораторных исследований.
- **Система отчетности:** Формирование выборок по 14 типам запросов (от списков врачей до статистики загрузки коек и выработки лабораторий).

## Дополнительные требования и ограничения  

- **Интерфейс:** Должен быть максимально простым и интуитивным, так как пользователи — врачи и медсестры, у которых мало времени на освоение сложных меню. Приоритет — скорость ввода данных.
- **Платформа:** Веб-приложение (доступ с любых компьютеров в сети больницы/поликлиники), не привязанное к конкретной ОС.
- **Безопасность:** Строгое разграничение прав доступа. Врачи видят только своих пациентов и свои назначения. Администраторы управляют справочниками. Данные пациентов должны быть защищены (соблюдение врачебной тайны).
- **Целостность данных:** Нельзя удалить отделение, если в нем есть пациенты; нельзя уволить врача, если у него есть активные пациенты на лечении.
- **Производительность:** Быстрый отклик при формировании сложных отчетов по большому объему историй болезней.

## Целевая аудитория проекта  

- **Лечащие врачи и узкие специалисты:** Для ведения карт пациентов, назначения лечения и просмотра анализов.
- **Заведующие отделениями:** Для контроля загрузки палат, распределения коек и мониторинга работы подчиненных.
- **Регистратура поликлиники:** Для записи пациентов и ведения первичного учета.
- **Главный врач / Администрация:** Для получения сводной статистики, анализа эффективности работы учреждения и кадрового планирования.
- **Сотрудники лабораторий:** Для внесения результатов анализов.

## Основные хранимые сущности

Ниже приведен список ключевых объектов системы и их основных атрибутов. Обратите внимание на различия в атрибутах для разных типов врачей.

| Сущность | Атрибуты | Примечания |
| :--- | :--- | :--- |
| **Медицинское учреждение** | `id`, `название`, `тип` (больница/поликлиника), `адрес`, `id_прикрепленной_больницы` (для поликлиник) | Поликлиники могут быть прикреплены к больницам |
| **Корпус** | `id`, `номер_корпуса`, `id_больницы` | Только для больниц |
| **Отделение** | `id`, `название`, `специализация`, `id_родителя` (корпус или учреждение), `кол_во_палат`, `кол_во_кабинетов` | Специализация важна для маршрутизации пациентов |
| **Палата** | `id`, `номер`, `кол_во_коек`, `id_отделения`, `текущее_кол_во_занятых_коек` | Для стационара |
| **Кабинет** | `id`, `номер`, `id_отделения` | Для поликлиники |
| **Сотрудник (Базовый)** | `id`, `ФИО`, `должность`, `категория` (врач/медсестра/санитар/уборщица), `стаж`, `id_учреждения` (основное) | |
| **Врач (Расширение)** | `id_сотрудника`, `профиль` (хирург, терапевт...), `ученая_степень` (кандидат/доктор/нет), `ученое_звание` (доцент/профессор/нет) | |
| **Хирург/Стоматолог/Гинеколог** | `число_операций`, `число_летальных_исходов` | Спец. атрибуты для оперирующих врачей |
| **Рентгенолог/Стоматолог** | `коэф_вредности` | Доплата за вредные условия |
| **Невропатолог** | `длительность_отпуска` | Спец. условие отпуска |
| **Место работы (Совместительство)** | `id_врача`, `id_учреждения`, `тип_занятости` (совместительство/консультация) | Врач может работать в нескольких местах |
| **Пациент** | `id`, `ФИО`, `дата_рождения`, `пол`, `адрес`, `полис_ОМС` | |
| **Амбулаторная карта** | `id`, `id_пациента`, `id_поликлиники`, `история_болезней`, `назначения` | Ведется в поликлинике |
| **Стационарная карта** | `id`, `id_пациента`, `id_больницы`, `id_палаты`, `id_лечащего_врача`, `дата_поступления`, `состояние`, `температурный_лист` | Ведется в больнице |
| **Операция** | `id`, `id_пациента`, `id_врача`, `дата`, `тип`, `исход` | |
| **Лаборатория** | `id`, `название`, `профили` (биохимия, химия...), `список_договоров` | Обслуживает учреждения по договору |
| **Анализ** | `id`, `id_пациента`, `id_лаборатории`, `тип`, `результат`, `дата` | |
| **Договор** | `id`, `id_лаборатории`, `id_учреждения`, `сроки`, `условия` | |

> **Важные нюансы моделирования:**
> 1. **Наследование врачей:** В базе данных это можно реализовать через отдельную таблицу `Doctors` с общими полями и таблицы-расширения (`Surgeons`, `Radiologists`) со специфическими полями, либо через JSONB поле для гибких атрибутов, либо через таблицу `Doctor_Attributes` (ключ-значение).
> 2. **Связь Пациент-Врач:** В поликлинике связь "многие-ко-многим" (пациент ходит к разным врачам), в больнице на конкретный момент времени — "один-ко-многим" (один лечащий врач).

> 3. **Ученые звания:** Звание профессора возможно только при наличии степени доктора наук, доцента — кандидата. Это нужно проверить на уровне бизнес-логики.
